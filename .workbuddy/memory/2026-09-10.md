### 根因定位与解决（18:25）—— 重要，后续会复现

**根因不是平台清理进程，而是本机（cnb.cool 云开发环境）无法让 git 在 `.git/refs/heads/` 下新建子目录。**

判定实验：
- `git update-ref refs/heads/zz-probe f13a4c93` → **持久**（扁平名，无需子目录）
- `git update-ref refs/heads/feature/groupbuy f13a4c93` → 返回成功但 ref 永不落地（需要 `feature/` 子目录）
- 手动 `mkdir -p .git/refs/heads/feature` + `echo <sha> > .git/refs/heads/feature/groupbuy` → **持久**
- 对比：`echo probe > .git/refs/heads/zz-file`（扁平）→ 持久

结论：**git 自己创建 `refs/heads/<ns>/` 子目录的动作会被撤销**，导致嵌套分支名的 ref 丢失。表现为 `git commit` 成功（对象与 reflog 都写入）但分支不前进，HEAD 变悬空、`git status` 报 "No commits yet"、索引里全部文件变成暂存态。

**可靠的解法（已验证）：**

```bash
# 1) 手动建目录并写松散 ref
mkdir -p .git/refs/heads/feature
echo "<commit-sha>" > .git/refs/heads/feature/groupbuy
# 2) 打包进 packed-refs —— 打包后的引用不会再被撤销
git pack-refs --all
```

打包后即使松散 ref 被删，分支依然存在。**每次在该分支上 git commit 之后都需要重复第 1、2 步**（提交对象是好的，只是 ref 没前进，用 reflog 尾部取新 sha 即可）。

### "重新拉库能否解决"的验证结论（18:30）

用户问删除文件重新克隆能否绕开该 quirk。做了对照实验，结论是**不能**：

**实验 A：当前仓库里换一个全新嵌套命名空间**
```

```
说明问题不限于 `feature/`，而是**这个 `.git` 中所有嵌套 ref 都无法持久化**（扁平名如 `zz-probe` 正常）。

**实验 B：在 D: 盘新建本地克隆，测试嵌套分支**
```

```
结果：克隆**自身就已损坏**——
- `.git/refs/heads/` 为空，本地分支一个都没建出来
- HEAD 悬空，`warning: remote HEAD refers to nonexistent ref, unable to checkout`
- 工作区**一个文件都没有签出**
- 只有 `refs/remotes/origin/*` 存活（因为它们进了 **packed-refs**）

这条"远端跟踪引用完好、本地分支全丢"的现象，正好再次印证根因是**嵌套松散 ref 无法持久化**。

**✅ 更安全的改写方法：完全绕开工作区，只构造新对象。**
读取原始提交对象，替换 `author`/`committer` 行里的名字并重接 `parent`，再用 `git hash-object -t commit -w --stdin` 写回：

```python
raw = git('cat-file','commit',sha)

# 逐行：author lsj → author ssd；committer lsj → committer ssd；parent → 新父
```

全程不签出、不碰工作区，因此**没有目录丢失风险**。之后写松散 ref + `git pack-refs --all`。
